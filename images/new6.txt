4.2 Does any existing value mean "ADD-only evidence that enables
specificity/reachability"? NO.
- corroboration-added = SUPPORT only; it does not assert that the
  candidate's reachable specificity changed because of the ADD.
- lifted-insufficient-to-supported = EVIDENCE-STATE lift, with
  precondition coreEvidenceState.status = insufficient. MT-1 keeps
  coreEvidenceState = supported in BOTH plugin states (NEW-4 CLOSED:
  truth-table row 1 unchanged); the transition is in REACHABILITY
  (L1-only → L1+L2), not in evidence status. Applying
  lifted-insufficient-to-supported to MT-1 would be a category error:
  it would assert a false evidence-state transition AND collide with
  NEW-4's row 1.
- The two lifts live on DIFFERENT dimensions:
    EVIDENCE-STATE lift:  insufficient → supported  (core-side status)
    SPECIFICITY lift:     L1 reachable → L2 reachable (reachability)
  They are NOT interchangeable and the contract needs BOTH.

4.3 Is the PLUGIN_SUPPORT vs PLUGIN_SPECIFICITY_LIFT distinction
genuinely required? YES — by contract evidence, not preference:
  (i) Protocol Audit 缺口 2 names the missing value verbatim.
  (ii) Hardened §15.3 establishes the governing discipline for ALL
       plugin-caused lifts: explicit registration, core state
       preserved verbatim, never presentable as "Core independently
       detected event". A specificity lift is the same discipline
       applied one dimension over; without a dedicated value the
       discipline CANNOT be executed for MT-1 (there is nothing to

  (iii) NEW-4 (CLOSED) made "L2 reachable ONLY via the explicit
       SCHOOL-DEPENDENT school gate" a load-bearing plugin-ON
       semantic; an unloadable assertion is not an auditable one.
  (iv) Auditability/OFF-ON reproducibility: with only
       corroboration-added, a W-1-style pure corroboration ADD and an
       MT-1-style gate-enabling ADD are snapshot-indistinguishable;

§5 SCHOOL DEPENDENCY AUDIT

5.1 The three distinct claims (task §7)
  1. A plugin was used.
     Carrier EXISTS: pluginManifest (§15.6, module+version) and
     schoolModulesUsed ([ModuleID], Hardened §17.2 Q13).
  2. A plugin contributed evidence.
     Carrier EXISTS: pluginEvidenceState.modules[] with
     contribution != none + addedEvidenceRefs (§15.4).
  3. The candidate DEPENDS on that plugin for L2 REACHABILITY.
     Carrier DOES NOT EXIST (snapshot level). This is the gap.

The three are NOT automatically equivalent — each has an independent
falsifier: (1) can hold with contribution = none (module enabled, no
evidence added); (2) can hold with no L2 effect (a corroboration-only
ADD on family-level evidence); (3) can hold with (1) false in the OFF
run (dependency exists even while the plugin is disabled — the OFF run
has empty schoolModulesUsed yet MT-1's L2 REMAINS school-dependent by
class declaration). (3) is a property of the CLASS + candidate state,
not of module usage.

5.2 The §7 test: schoolModulesUsed != proof of specificity dependency
VERDICT: CONFIRMED — the contract does NOT explicitly say otherwise.
Hardened §17.2 declares schoolModulesUsed: [ModuleID] with no
semantics beyond usage disclosure (Q13); no Registry clause binds it
to L2 dependency. A counterexample within the existing contract
confirms non-equivalence: plugin enabled + corroboration-only ADD on
an L1-family evidence item → schoolModulesUsed non-empty, zero L2
dependency. Therefore a separate semantic carrier IS required for
claim 3.

5.3 Carrier decision (DO NOT add the field — task §7)
REQUIRED CARRIER = a DERIVED-SEMANTIC registration rule (the Hardened
§15.5 precedent: derivedPluginIndependence: Bool is mechanically
derived from coreEvidenceState — derived facts need no independent
storage):
  For any candidate whose eventClass belongs to a class with
  R1 = SCHOOL-DEPENDENT (Registry) — equivalently, whose master-matrix
  row states "core 判据不足以独立达 L2":
    the record's school-dependency status for its L2 identity is
    mechanically TRUE, derived from (class declaration + master
    matrix); schoolModulesUsed (and, when ON,
    pluginEvidenceState.modules[].moduleID) DISCLOSES the concrete
    module(s) through which the gate is satisfied.
  Scope guards (semantic overload prevention):
    - Applies ONLY to L2 records of SCHOOL-DEPENDENT classes.
    - NEVER annotates an L1 record (L1 family existence is
      core-backed; NEW-4 X-7 forbids school-dependent annotation on
      the L1 record).
    - Adds no field, no enum, no numeric; pure derivation rule text in
      the Registry EventSnapshot contract.
This carrier, together with the §4 lift value, makes claim 3 explicit,
auditable, and mechanically checkable WITHOUT schema change.
